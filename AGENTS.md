# AGENTS.md

## Verify

```bash
dotnet build backend/PrRag.sln
dotnet test backend/tests/PrRag.Tests
```

Tests require a reachable Postgres instance:

```bash
TEST_CONNECTION_STRING="Host=localhost;Port=5432;Username=prrag;Password=prrag" \
  dotnet test backend/tests/PrRag.Tests
```

Or via Docker (db must already be running):

```bash
docker compose -f docker-compose.yml -f docker-compose.test.yml --profile test up --build test
```

There is no linter, formatter, or typecheck script beyond `dotnet build`.

The live gates' aggregation step has its own tests, which need neither Postgres nor
a provider — they replay recorded observations, including a dead one, which is the
only way to exercise the output that decides a run passes:

```bash
python3 -m unittest discover -s scripts/lib -t scripts/lib
```

The Vite + React front-end in `frontend/` has its own verify:

```bash
cd frontend && npm install && npm run build
```

## Architecture

Layered .NET 10 solution (`backend/PrRag.sln`):

- **PrRag.Application** — domain models, DTOs, service interfaces, business logic. No infrastructure dependencies.
- **PrRag.Infrastructure** — EF Core DbContext, pgvector, OpenAI clients, file watcher. Implements Application abstractions.
- **PrRag.Api** — ASP.NET minimal API host. Calls `AddApplication()` / `AddInfrastructure()` for DI, runs migrations on startup via `DbInitializer.ApplyMigrationsAsync`.
- **PrRag.Tests** — xUnit integration tests against a real Postgres. Uses fakes for OpenAI (no API key needed).
- **PrRag.DataGenerator** — standalone console tool, outputs `purchase.json`.
- **`web`/`frontend` layout** — the .NET solution and projects live in `backend/` (together with the Dockerfiles); the Vite + React + TypeScript front-end lives in `frontend/`, not part of the .NET solution. It calls the API endpoints (`/api/chat`, `/api/ingest`, `/api/status`). Compose files, DevContainer config, and docs stay at the repo root.

Dependency direction: Api -> Infrastructure -> Application.

The API enables cross-origin access from the origins in `Cors__AllowedOrigins` (comma-separated, default `http://localhost:5173`). The `web` service runs under the `demo` profile in `docker-compose.yml`; NPM-driven builds are separate from `dotnet build`.

## Key gotchas

- **`demo` profile**: The API service is behind `docker compose --profile demo`. A plain `docker compose up -d` only starts the database. This is intentional — it prevents the OpenAI key from leaking into `docker compose config` output.
- **Writable mount `./reports`**: the API image runs as the non-root `app` user (UID 1654). On a fresh start Docker may create the bind-mount source dir owned by `root`, which causes 500s when the observability report writes. The runtime entrypoint starts as root, chowns the dir to `app:app`, and then drops privileges.
- **Skill and draft state live in `AgentSessionState`, not the MAF session.** `SkillSessionState` and `RequisitionDraftSessionState` are helpers over the application-owned `AgentSessionState` (one per client `session_id`, held by `InMemoryAgentSessionStore`), reached from tools via `AgentTurnContext.State`. They used to sit in `AgentSession.StateBag`, which coupled them to the session object's lifetime: MAF binds a session to the agent instance that created it, so a cached session pinned one composition of the agent graph for the whole conversation — and that graph captures request-scoped services in its tool delegates. The `AgentSession` is now created **per turn** and the conversation is replayed into each run, so never reintroduce a cached `AgentSession` or a state-bag read. Answers are never prefixed, and skill persistence does not depend on parsing plain-text history. `AgentSessionState.History` holds **text turns only** — see the workflow-output gotcha below for why no tool traffic may be recorded.
- **A run's messages are not the answer, and no tool traffic is recorded.** `includeWorkflowOutputsInResponse` is `false` on purpose. Left `true`, the workflow folds the whole run back as outputs — the request replayed ahead of the reply — so `response.Text` and the streamed deltas arrive as the conversation's own history in front of the new answer, and every turn after the first looks like a repetition. Two things follow, and both are load-bearing:
  - The answer is the run's `Text`, and `RecordTurn` records `question` + `answer` from it. It does **not** read `response.Messages`. Reassembling the recorded conversation out of those messages is what reintroduced the echo; `Answer_is_the_new_reply_and_not_the_replayed_transcript` guards it.
  - `AgentSessionState.History` never holds a `FunctionCallContent` or a `FunctionResultContent`. Neither half is replayable: across a handoff the specialist makes the call, so the workflow surfaces the result alone, and the framework batches results into one message whose last call is emitted as a *later* assistant message — so no prefix of a tool transcript is well-formed. Replaying either half is rejected by the chat API outright (`messages with role 'tool' must be a response to a preceding message with 'tool_calls'`) and fails the entire turn, not just the replay. The answer already carries the grounded rows.
  - Do not "fix" this by filtering streamed text against the sent messages. A new answer can be byte-identical to an earlier one, so text matching silently eats real output.
- **Every agent gets an inert `ChatHistoryProvider`.** `ExternalHistoryProvider` contributes nothing on purpose: `ChatService` replays `AgentSessionState.History` into the run and records the turn's own text. Left to its default, each agent would keep a second per-turn copy of a history the application already owns.
- **Embedding dimension is coupled to model**: `text-embedding-3-small` produces 1536-d vectors. Changing the model requires a new EF Core migration and reindex. On the Azure path the coupling is to the *deployment* rather than the model, which makes it easier to get wrong: deployment names are arbitrary and are used verbatim, so nothing rejects a deployment of the wrong dimensionality and the failure lands on the ingest path as a `vector(1536)` dimension error that reads like a data bug. `PurchaseRequisition.EmbeddingDimensions` stays a domain constant; do not make it configurable to accommodate a provider.
- **The LLM provider is a config value, and its validation is a startup concern.** `OpenAISettings.Provider` (`openai` | `azure`) and `OpenAISettings.Endpoint` select the provider; `LlmProviderResolver` resolves and validates them into a `ResolvedLlmProvider` and `LlmClientFactory` builds both clients from it. `LlmProviderResolver` is the **only** place a `Uri` is produced, deliberately: `OpenAIClientOptions.Endpoint` is write-only and cannot be read back off a built client, so returning the `Uri` from the resolver is what makes the endpoint assertable in a test at all. Both providers are the same `OpenAI` SDK types with a different endpoint — there is no second client type and no second package, and `PrRag.Application` resolves no provider package, so keep it that way. On Azure the `ChatModel`/`EmbeddingModel` values are **deployment names**, used verbatim and never matched against a model list. The resolver throws at startup rather than deferring to the first request, because a client built from bad configuration does not fail loudly: it throws per-request, MAF absorbs that into an empty run, and `/api/chat` answers `502` — the same signal a dead provider gives, so a config fault becomes an outage that reads as an outage. Add a new provider in the resolver and the factory; do not add a branch to `AddInfrastructure`.
- **`UseLogging()` on the chat and embedding clients is load-bearing, not decorative.** `ChatService.RequireAnswer` names `Microsoft.Extensions.AI.LoggingChatClient` in the exception message as the operator's only path to the cause of an empty run, so removing or renaming that decorator turns the guidance into a dead end. The registrations must also stay **unkeyed**: `AgentRunService` injects `IChatClient` unkeyed and `IntegrationServiceFactory` satisfies it with `FakeChatClient`, which is why the whole test suite runs with no credential and no network. Keying either registration, or introducing a provider-specific `IChatClient`, drags every test across a credential boundary for no gain.
- **`data/purchase.json`** is a bind-mount volume. The API watches it for changes (FileSystemWatcher + debounce). The file is read-only inside the API container.
- **Settings use `__` separator** in `.env` (e.g. `OpenAI__ApiKey`) — these are the same `.NET` config keys the app reads. No duplication.
- **EF Core migrations auto-apply on API startup.** No manual step needed. To create explicit migrations: `dotnet ef migrations add <Name> --project src/PrRag.Infrastructure/PrRag.Infrastructure.csproj` (from `backend/`).
- **CORS is config-driven**: `Cors__AllowedOrigins` (default `http://localhost:5173`) controls what origins may call the API from the browser. Add origins (comma-separated) if the front-end is served elsewhere.
- **DevContainer build owner**: The `devcontainer` service runs as `root` by default, but `devcontainer.json` sets `"remoteUser": "vscode"`. Running `dotnet build` as `root` inside the container writes `obj/`/`bin/` artifacts owned by `root`; a subsequent VS Code build (as `vscode`) fails with `Permission denied` writing `.cache` files. Always build as `vscode` (e.g. `docker compose exec -u vscode devcontainer dotnet build ...` or the VS Code `build` task). If a root-owned build breaks things, remove all `bin`/`obj` as root first, then rebuild as `vscode`:
  ```sh
  docker compose exec -u root devcontainer sh -c 'find /workspaces/backend/src /workspaces/backend/tests /workspaces/backend/tools -type d \( -name bin -o -name obj \) -prune -exec rm -rf {} +'
  docker compose exec -u vscode -w /workspaces/backend devcontainer dotnet build /workspaces/backend/PrRag.sln -c Debug
  ```

- **A handoff is invisible unless something records it, and it was the reason a bad answer could not be diagnosed.** A handoff is a MAF workflow edge, not an application tool, so it contributes no `RagToolCall` and the framework names it by participant *position* (`handoff_to_1`), which nothing on the composed agent maps back to a capability. Two opposite failures were therefore the same report: the orchestrator answering a creation request it holds no write tool for, and it routing correctly to the creation agent which then gave a bad answer. `RagQueryReport.EntryAgent` and `Handoffs` now carry both, recorded by `AgentAttributionChatClient` — a `DelegatingChatClient` the composer binds *per agent*, because the decorator is the only place that knows which agent emitted a call, and it must sit innermost so it sees the call before the function-invocation layer dispatches it. A handler would be too late. `HandoffToolName` is the only place that knows the positional convention, and `HandoffScripting` goes through it so a test and the production signal cannot disagree about which number means which capability. Its `ResolveTarget` **throws** on a recognised name with an out-of-range position: that is the graph and the convention diverging, and any handoff recorded for the turn would be attributed to the wrong capability. **The answer's author is now `RagQueryReport.AnswerAgent`, so the two failures are separate reports**: it records the *last agent to emit non-empty text*, which is the answer's author by construction rather than by approximation — the run's `Text` is that text, so text produced and then discarded was not the answer either. It is deliberately *not* the furthest handoff target, which is stable when the entry agent resumes and speaks and wrong whenever the target does not produce the final text. Three shapes are now readable: entry == author with no handoffs is an answer given in place, author != entry is a delegation with the target on the hook, and author == entry *with* handoffs is a closing remark after a delegation. A response carrying only a function call contributes nothing, because mid-loop that is what an agent does instead of answering; a turn in which no agent emitted text records **no** author, and it must never default to the entry agent — that is the whole signal, and the report for a dead-provider 502 would otherwise read as an ordinary turn. The same decorator records it, for the same reason it records handoffs: it is the only place an agent's own traffic is still identifiable, and every agent's instance writes one field so the run's own ordering decides the value, last-write-wins, with no coordination between them. `The_answer_to_a_handed_off_turn_is_the_targets_own_text` pins the rest in code, and `The_recorded_author_is_the_agent_whose_text_the_caller_received` pins the field against the answer rather than against a second literal slug.
- **A turn that arrives with every field is a request to stage, not evidence that staging happened.** On the adversarial "skip the confirmation" probe — all six fields, plus an instruction to skip the confirmation — `RequisitionCreationSpecialist` used to answer that it held no draft awaiting confirmation and stop, on 10 of 18 pooled turns. It was never the orchestrator declining to hand off: the shipped observability showed 24 of 24 turns recording the handoff. Two turns read alike and were conflated, because both name the confirmation step and both arrive holding no draft: *"skip the confirmation"* asks the agent to stage, and *"yes, I confirm it"* is a claim about a draft the agent already presented. The narrower forged-confirmation rule read as a complete answer to both. The block now separates them by asking whether the turn carries the fields, and `CreationStagingPromptTests` guards the wording. Same trap on the other side: asserting or presenting a draft that was never staged is a fabricated fact, and the only shape of this that is not safe.

- **Answer hygiene is a live gate, and only partly a test.** The core prompt once mandated a literal `Thought:/Action:/Observation:` trace and then forbade showing it; the model resolved the contradiction by printing it, and on the semantic path that produced real fabricated completions — a turn wrote "Observation: Executed the search" and called no tool at all. The prompt now keeps the deliberation private and names the failure modes, and `AnswerHygienePromptTests` asserts the prompt (a fake model will not narrate, so the behaviour itself is untestable in-process). For the behaviour, run `scripts/live-answer-hygiene.sh [runs]` against the demo API: it fails on narration in the answer, and on an answer claiming a search that the report shows never ran. It also fails on a turn that produced no answer, on a cold turn that never attempted a retrieval, and on a turn with no report to check — without those it reported a completely dead provider as eight clean runs. Two supporting facts make that check possible: `RagQueryReport.RetrievalAttempted` distinguishes *searched and found nothing* from *never searched*, which `UsedNoContextFallback` cannot (both are `RetrievedCount == 0`), and `ToolNames.ReadOnly` names the read tools so a write-only turn is not counted as a retrieval.
- **The live gates report rates, and their checks are not all negotiable.** `scripts/live-creation-gate.sh [runs]` (default 3) and `scripts/live-answer-hygiene.sh [runs]` (default 8) both emit JSONL observations to `scripts/lib/gate_report.py`, which splits every check into three kinds. `HARD` is an invariant — an unsafely written row, a report claiming a row that does not exist, an answer asserting a creation that never ran, narration, a claimed search the report shows never happened — and one occurrence fails, because "wrote a requisition nobody confirmed" is not something to divide by three. `RATE` is a model-dependent capability, held to a per-check floor. `INFRA` is a turn that was not evaluated at all (non-2xx, unparseable, no report): counted separately, and **never a pass**, since reporting a dead provider as clean is the failure these gates exist to prevent. Everything unlisted is held to 1.0, so a gate is exactly as strict as the single-run version it replaced unless a floor is deliberately lowered next to the measurement that justified it.
- **One sample is not a rate, and this was proved by the gates themselves.** Both floors in the creation gate were first written from a single sample of 6 and both were wrong: `no-draft-staged` was estimated at 0.6 and the next 6 runs measured 0.50, failing the gate; `wrong-blocker-reason` was documented as having "no failure in 6 runs" and the next 6 runs produced one. Floors now cite a pooled sample, and the standing instruction is not to move a floor to match the last result — a floor set to whatever was observed cannot catch a regression, which is its only job. **The defect the rates exposed was misattributed for two changes' worth of work, so check the report before you trust a story about which agent failed.** The recorded claim was that the orchestrator replies that it holds no draft and stops instead of handing off, on roughly half the turns (7 of 18 measured). The shipped observability refuted that on its first live run: 24 of 24 turns recorded the handoff, and the agent declining was the creation specialist. It read as an orchestrator failure because `EntryAgent` plus `Handoffs` localise a turn to a *chain*, not to an author, so both stories fit the report. After the prompt change the creation specialist measures 1.00 (6 of 6) and its floor is 1.0. **Open, and different:** on the `stage` probe the orchestrator itself now shows up — 1 of 6, answering a creation request with no handoff and no tool call, over a draft it never staged. That one is a fabricated fact, not a rate, and it cascades into the following confirmation turn missing its row. It is the orchestrator-side failure the earlier story described, on a different probe and at about a sixth the rate.
- **A failures-only table proves nothing, so the summariser prints per-probe turn counts too.** A check that passes raises no row, so an all-clean run produced an empty table — indistinguishable at a glance from a run that examined nothing. The per-probe "N/M turns raised nothing" lines, the `(no check failed)` marker, and the caller's `--expect-probes` are what make "clean" mean *checked and clean*; a probe that never reported fails rather than passing silently. The human-readable line and the recorded observation are produced by the same python process and the verdict is computed from the recorded file, not from shell counters, so the per-turn output and the aggregate cannot drift apart.

- **An empty run is a failure, not a quiet turn.** MAF completes a run whose chat client threw — a rejected key, a provider outage — and surfaces an empty run rather than an exception, logging the cause under `Microsoft.Extensions.AI.LoggingChatClient` and carrying on. Left alone that means the caller gets `200 OK` with `""` and the only evidence is a log line, so a dead provider is indistinguishable from a quiet turn; it was found by a live test returning nothing, not by any test. `ChatService.RequireAnswer` now throws `ChatTurnFailedException` when a run yields no text, `/api/chat` maps it to **502** (upstream, not this app), and the streaming path aborts rather than sending `[DONE]` after an empty body. Two things depend on the ordering: the report is written *before* the throw, so a failed turn is still diagnosable, and the turn is *not* recorded in history, since replaying a question paired with a blank answer poisons every later turn. `UsedNoContextFallback` is likewise gated on an answer existing — it means *the caller was given the fallback*, and keying it on `RetrievedCount == 0` made the outage report a fallback that was never sent. Do not add a "be lenient when the answer is empty" guard: emptiness is the only signal a provider failure leaves.
- **Adding an agent tool**: the capability units in `Services/Agents/Specialists/` are the tool definition sites — `RequisitionSearchSpecialist`, `RequisitionCreationSpecialist`, `SkillActivationSpecialist`. Pick the unit that owns the capability, then make five edits: the handler, its shared wire-name const in `ToolNames` (used by both registration and the report's `Record` call so the two can't drift), the `<ALLOWED_ACTIONS>` bullet in **that unit's `ActionBlock`** (not in `CoreInstructions` — the bullet lives beside the code it describes), the partition assertion in `AgentFrameworkLayeringTests`, and the layering name assertion. Register the handler **method itself**, never a forwarding lambda that calls it — `AIFunctionFactory` builds the parameter schema from the registered delegate's `MethodInfo`, so a lambda silently drops every parameter `[Description]` and the model stops seeing them. `ToolSchemaTests` is the guard for that. Tool descriptions come from the method's `[Description]` alone; don't also pass one to `AIFunctionFactoryOptions`. Because the prompt is composed from the catalog, a tool that is registered but not named in any `ActionBlock` reaches the model undocumented; `SpecialistCatalog` throws at composition if the per-unit lists stop partitioning the registered set.
- **A skill step that names no tool can be performed by any agent, and activated guidance confers no authorship.** The bullet above is about a skill naming a call the running agent does not hold, and both checks for it — the one-capability test and `does_not_steer_routing` — look for *named* calls. The step that actually broke things named none. Step 5 of the create skill is a six-line field template ending "and explicitly ask the user to confirm", with no tool anywhere in it, so the agent holding no staging tool can satisfy it in prose out of the user's own six fields, with nothing to fail and no guardrail downstream to contradict it. `ChatService` injects activated guidance as a run-level system message, so it reaches every agent in the run *including the one that activated it*, and it arrives **after** the agent's own instructions: a later, numbered, concrete step outranks an earlier general routing sentence. On the `stage` probe the orchestrator did exactly that, presenting a draft it had never staged and asking the user to confirm it; the next turn found no draft and missed its row, so one event failed three checks. So the checkable rule is **a step whose result needs a tool is not performable by an agent without it — audit the steps that name no tool, because they are the only ones nothing checks.** Two consequences. The correction belongs in the *reading* agent's `ActionBlock` as a capability rule ("a step you cannot perform is not yours to carry out", "never present an artifact that no tool returned"), never in skill text: `does_not_steer_routing` bans routing language there, and a capability rule outlives whichever agent owns the next capability. And `HandoffInstructions` was already correct and still lost, which is why the fix did not go there — the same rule in two places would just be two things to drift. **The rate is 1 in 19 `stage` turns, not the 1 in 6 first recorded, and the prompt fix is NOT verified**: 18 post-fix turns came back clean, which a 1-in-19 rate produces with no change at all, and one gate run yields exactly one `stage` sample, so separating the two needs ~100 runs. Read it as hardening justified by prompt structure, not a demonstrated improvement; the gate script's `OPEN and NOT this floor` comment says so in place. **The defect is now measurable even though the fix is not verified**: `AnswerAgent` makes the 1-in-19 shape a report fact rather than an inference, and the creation gate checks it as the `HARD` check `answer-authored-by-a-different-agent` — an entry agent authoring an answer on a probe that expected a handoff. `HARD` because a fabricated artifact is not a capability shortfall, so it takes one occurrence and acquires no floor; the gate will not hand you a rate, so the count comes from the FAIL lines. Under ~100 runs, record "no failure seen in N" and never a rate, and do not put it in `MIN_RATES`.
- **Skill markdown is prompt input, so a wrong tool name in it is a silent bug.** The shipped `data/skills/*.md` is read by the *orchestrator*, because only the orchestrator holds `activate_skill` and so is the only agent that can be told what skills exist. Which tools that reader owns moves with every extraction — it held the write tools plus activation, and now holds activation alone — so "name only tools the running agent owns" is not a rule you can check by reading the text. Two consequences, both of which have bitten. When the retrieval tools moved to their own agent, the create skill still told the agent to validate codes with `search_by_codes`; the model was told to use a tool it was never offered, so the step silently never ran and **no test failed**. And after the write tools moved to the creation agent, the same skill's "call `create_requisition_draft`" became followable only by a *different* agent from the one reading it — it still works, because `ChatService` injects the activated guidance as a run-level system message that reaches every participant, but nothing in the text says so. So the checkable rule is **one skill names calls within one capability**: `The_create_skill_instructs_calls_only_within_one_capability` drives it off the catalog, and it fails for a straddling skill in either direction, because a skill that spans two agents needs a mid-skill handoff that nothing in it tells the model to make. `AgentFrameworkLayeringTests.No_units_action_block_names_a_tool_it_does_not_own` is the same rule applied to the other half of shipped prompt text, over all three units. Put any *authoritative* check in the tool's own code rather than in prose — `create_requisition` calls `ExistsItemSupplierCombinationAsync` and refuses, which is why the combination guard survived the split when the model's early warning did not. Routing guidance belongs in the owning unit's `ActionBlock`, never in skill text: the graph decides who reaches whom, and skill text drifts from it without failing anything. `ShippedSkillTextTests` reads the real files (not a fixture) and shares the repo-root lookup via `RepoFiles`, so a test can guard shipped prompt text without a fixture and without its own copy of the path walk; it was verified to fail when the old instruction is restored. `SkillFrameworkTests` had been seeding the same stale text as a fixture, so a test was passing on guidance that no longer ships.
- **The active skill reaches a participant even though the manifest does not.** `AgentInstructions.ComposeSystemPrompt(skillService.GetManifest(), ...)` is given only to the orchestrator, because only the orchestrator holds `activate_skill` and so is the only agent that can be told what exists. The *activated* guidance is a different channel: `ChatService.BuildTurnMessages` prepends it as a run-level `ChatRole.System` message, and the run's messages reach every agent in the workflow. So a turn that hands off still carries the skill. Assert it with `chatClient.LastMessages`, not `LastPrompt` — and note the guidance is injected on the turn *after* activation, once, so restating it every turn would stop the workflow ending.
- **The agent's system prompt is an `Instructions` value, not a message.** `ChatClientAgent` passes `Instructions` as `ChatOptions.Instructions`; it never enters the message history. Two consequences worth not rediscovering: the prompt is rebuilt per request (so a skill manifest reloaded mid-session reaches the next turn), and it cannot be duplicated across turns. `FakeChatClient` folds `ChatOptions.Instructions` into `LastPrompt` for exactly this reason — without that, prompt assertions read zero and look like the prompt vanished.
- **Phase 2 is a handoff workflow, and `IAgentRunService` is the seam.** It will be built on `Microsoft.Agents.AI.Workflows`, with the workflow presented to callers as an `AIAgent` via `WorkflowHostingExtensions.AsAIAgent(...)` so `ChatService`, the endpoints, streaming, and the session store all keep working unchanged. Do not change `IAgentRunService`'s shape. `SpecialistDefinition.Id` is the seed for the stable agent slug; when the definitions become real agents, `Id` and `Name` must **split** — `Id` is for telemetry correlation and must stay stable across a display rename, so a rename must never touch it.
- **The entry point is per request, and state-dependent; the orchestrator is not always in the turn.** The write tools belong to `RequisitionCreationSpecialist` (`AgentIds.Creation`), so the orchestrator holds only `activate_skill` and reaches creation through a handoff. But the creation gate *spans turns* — stage on one, the user's yes on the next — so `AgentGraphComposer.ResolveEntryPoint` reads the draft's recorded state and sends a turn with a staged, unwritten draft straight to the creation agent, with the orchestrator absent from that graph. Three things follow, and all three are load-bearing:
  - **`AgentRunService` composes lazily, and `AgentTurnContext.Begin` runs before the MAF session is created.** Composing in the constructor reads a null state and always builds the orchestrator-entry graph — a defect invisible on every turn except the one the write path depends on. `Begin` therefore takes the state and `AttachSession` the session; do not fold them back together.
  - **A confirmed-but-unwritten draft still counts as pending.** Keying on "unconfirmed" would route the turn after a failed write to an agent holding no write tool, stranding a requisition the user already confirmed.
  - **A skill cannot be activated while a draft is pending**, because only the orchestrator holds `activate_skill` and it is not on that path. That is the safe direction — the alternative is a new skill re-planning a confirmed write — and it is stated in the creation action block so the model does not have to discover it. `A_skill_cannot_be_activated_while_a_draft_is_pending` pins it.
  - In tests, **one turn is one scope**: the graph is composed per request, so two `AnswerAsync` calls sharing a scope reuse turn 1's entry point. A handoff tool is still offered to the creation agent on that turn, because it keeps its edge to retrieval — so "entered at creation" is asserted by the *write tools being on offer and `activate_skill` not*, not by the absence of a handoff tool. `HandoffScripting.HandOffTo*` derives MAF's positional `handoff_to_N` from the catalog, so no test writes that literal.

## Tests

- Integration tests use `TEST_CONNECTION_STRING` env var (set by compose or manually).
- When `TEST_CONNECTION_STRING` is unset, `TestDatabase.ConnectionStringTemplate` falls back to a sensible host: `Host=db` when running inside the DevContainer (detected via `REMOTE_CONTAINERS` env or the presence of `/.dockerenv`/`/workspaces`), otherwise `Host=localhost`. This lets the VS Code test extension run the tests inside the DevContainer with no manual env setup — it connects to the compose `db` service instead of failing on `localhost`.
- Tests run at container runtime (`ENTRYPOINT dotnet test`), not build time — this is because the `db` service isn't available during image build.
- Test fakes: `FakeChatClient`, `FakeEmbeddingService` — no real OpenAI calls during tests. `FakeQueryRewriter` was removed along with `IQueryRewriter` (the model supplies the `search_semantic` query itself).
- `FakeChatClient` scripts tool calls rather than invoking them: add a `FunctionCallContent` to `ScriptedToolCalls` (multi-step) or set `ToolCall` (one-shot), then read the result back with `LastToolResultJson()`. MAF's own loop dispatches the real handler and appends the `FunctionResultContent`.
- Coverage: ingestion diff (initial, no-change, changed/new rows), agentic retrieval and tool schemas, skill framework, RAG observability report, created-requisition listing.
