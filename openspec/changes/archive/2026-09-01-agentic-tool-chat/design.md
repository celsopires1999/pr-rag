## Context

The app is a layered .NET 10 RAG solution (`PrRag.sln`): `PrRag.Application` (domain/services, no infra deps), `PrRag.Infrastructure` (EF Core + pgvector + OpenAI clients), `PrRag.Api` (minimal API), plus `PrRag.Tests` integration tests with fake OpenAI clients. Chat is served by `ChatService`, which today forces a rigid retrieval pipeline on every question: regex-extract `ITM-*`/`SUP*` codes → exact `SearchByCodesAsync` → if results < `top_k`, `IQueryRewriter` → embed → `SearchAsync` vector query → stuff context into a system prompt. Streaming (`/api/chat/stream`) already accepts a `Messages` history, but the full conversation is only used as prompt filler; retrieval is always forced regardless of whether the question needs the DB.

The user wants: (1) turn the two PostgreSQL queries into **tools the chat model chooses whether/how to use**, and (2) send the **full conversation context** so chat is continuous across turns.

## Goals / Non-Goals

**Goals:**
- Let the chat model decide whether to call a retrieval tool (exact code lookup or semantic vector search), per turn.
- Send the complete conversation history to the model each turn and carry tool results into follow-ups for continuity.
- Keep `top_k` / `min_similarity` configurable and preserve the public API response shapes.
- Route both non-streaming and streaming through the same tool-calling flow.

**Non-Goals:**
- No change to the ingestion pipeline or database schema/embeddings.
- No prompt-engineering/server on chat fetch limits beyond the current defaults.
- No web UI rewrite beyond verifying it sends full history.

## Decisions

### Decision: Use Microsoft.Extensions.AI function-calling (AIFunction) for the two tools
The project already uses `Microsoft.Extensions.AI` (`IChatClient`, `ChatMessage`, `ChatResponseUpdate`). We create the two tool functions with `AIFunctionFactory.Create` and drive the invocation loop **manually in `ChatService`** (Application), using the primitives from `Microsoft.Extensions.AI.Abstractions` (`ChatOptions.Tools`/`ChatToolMode.Auto`, `AIFunction.InvokeAsync`, `FunctionCallContent`/`FunctionResultContent`).

- **Why this over `FunctionInvokingChatClient`**: The tool delegates must access the scoped `IPurchaseRequisitionRepository` and `IEmbeddingService`, and `ChatService` lives in `PrRag.Application` which intentionally references only `Microsoft.Extensions.AI.Abstractions` (no infra deps). A `FunctionInvokingChatClient` DI wrapper (from the non-abstractions package, in Infrastructure) would force tool functions to capture scoped services at a singleton registration, fighting the Application->Infrastructure dependency direction. The manual loop keeps the dispatch co-located with the scoped services and reads the raw (unmarshalled) tool results directly for both the model and the observability report.
- **Alternative considered**: Hand-roll the whole JSON tool schema + parsing. Rejected: `AIFunctionFactory` already generates the schema and binds arguments, so the manual part is only the small call/result loop.
- **Implementation detail**: `AIFunctionFactoryOptions.MarshalResult` is set to a passthrough delegate so `InvokeAsync` returns the raw `IReadOnlyList<RagRetrievedItem>` (used for `retrieved_count`) rather than the default JSON-marshalled value; optional delegate parameters default to `null` so the model can supply subset of `items`/`suppliers`.

### Decision: Two tools bound to the two existing queries
- `search_by_codes(items, suppliers)` → `IPurchaseRequisitionRepository.SearchByCodesAsync` (exact `ITM-*`/`SUP*`).
- `search_semantic(text)` → embed `text` with the configured embedding model, then `IPurchaseRequisitionRepository.SearchAsync(embedding, topK, minSimilarity)`.

The tool delegates call the existing repository methods directly (no repository interface change needed). The tool functions are declared in `ChatService`, which already holds the scoped repository and embedding service. The old regex-based dispatch and `IQueryRewriter` usage in `ChatService` are removed (rewriter may remain registered for other consumers).

### Decision: Full conversation context flows to the model every turn
The chat client receives `request.Messages` + the current `Question` as the message list. Tool results are appended as `FunctionResultContent` messages to the same conversation by the manual loop, so they persist into follow-up turns. This delivers the "continuous experience" requirement without a separate session store.

- **Why**: Simplest faithful reading of "full context" — everything the client already sends is forwarded; previous tool results remain in the continuing message chain.

### Decision: Grounded answer built from tool-retrieved context, graceful when unused
The assistant answer is generated by the model after any tool calls. If no tool returns usable context, the model answers from conversation alone (per the no-context scenario). `retrieved_count` is computed from the tool results returned in the final turn so `/api/chat` and `/api/chat/stream` shapes stay intact.


### Decision: Non-streaming and streaming share the same tool-calling flow
A single `ResolveContextAsync` method runs the tool loop (build conversation from the full history + current question → call the chat client → invoke any requested tools → append `FunctionResultContent` results → repeat) and is used by both `AnswerAsync` and `StreamAsync`. Only the final-answer consumption differs: non-streaming reads the final assistant `Text` directly; streaming waits for the same resolved final message and yields its text through the SSE endpoint followed by the completion signal.

## Risks / Trade-offs

- **Tool-call latency** → The model may take extra round trips deciding to call tools. Mitigation: keep only two tools, accept the small latency for correctness; tests use fakes.
- **Retrieved count semantics change** → `retrieved_count` now reflects tool results for the current turn rather than the old top-K algorithm. Mitigation: document in specs; keep `top_k`/`min_similarity` controls.
- **Full history token growth** → Longer conversations increase tokens. Mitigation: rely on the client to cap history; out of scope to add server-side trimming.
- **Tool schema drift from real queries** → If the repository query signatures change, tool delegate signatures must be updated. Mitigation: wire delegates directly to repository methods so types flow through.
- **IQueryRewriter no longer used by chat** → Its tests/consumers may need review. Mitigation: keep the abstraction/registration; note in tasks.

## Migration Plan

1. Add tool-facing retrieval methods/delegates to `PurchaseRequisitionRepository`.
2. Build the two AIFunctions and the manual tool loop in `ChatService` (Application) — no DI-wrapped chat client change in `AddInfrastructure`.
3. Rework `ChatService` to forward full history + question into the tool-calling client and read results.
4. Update the chat DTO handling and keep `top_k`/`min_similarity`.
5. Update tests/fakes and verify `dotnet build` + integration tests; verify `web/` sends full history.
6. Rollback: revert `ChatService`/DI to prior commit; API contract unchanged.

## Open Questions

- Does the client send the full rolling message history, or only the last N turns? Affects how much continuity the model sees.
- Should `top_k`/`min_similarity` still be accepted per-request, or become server-config-only?
