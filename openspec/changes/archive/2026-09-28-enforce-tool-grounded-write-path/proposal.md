## Why

The Azure/gpt-5-mini gate run in `2026-09-27-add-azure-openai-provider` §5.6 recorded two invariant violations, and both are the same defect wearing different clothes: **shipped prompt text tells an agent to assert a fact that only the application's session state holds, and the model complies.** No floor moved, and the honest reading recorded there was that the write path needs re-measuring on this model. The reports behind that run are still in `reports/`, and they are more specific than the summary.

**The creation agent denied a draft the application had staged — 3 of 3 confirm turns.** Every one of those reports reads `EntryAgent=prrag.creation`, `AnswerAgent=prrag.creation`, `tools=[]`, and answers "I don't have a requisition draft awaiting confirmation in this session." The entry point is not a guess: `AgentGraphComposer.ResolveEntryPoint` sends a turn to the creation capability *only* when `HasUnwrittenDraft` is true, so the turn was routed there precisely because a draft existed — the previous turn's report says `staged=true` with the handoff recorded. Meanwhile `RequisitionCreationSpecialist.ActionBlock` says: *"Only one shape is a question about draft state: the user is answering a draft you actually presented — 'yes, I confirm it' — and you hold none. Then, and only then, say that no requisition draft is awaiting their confirmation."* The antecedent is checkable from the conversation; the consequent is a fact only the application holds; and the rule nowhere says to check it. The user's turn was literally "Yes, I confirm it", so the model took the consequent. The counter-evidence was already in its context — the recorded conversation shows the draft it staged — and lost to the rule. This rule was added by an earlier change to fix a *different* failure, and it is a licence rather than a prohibition, so a model that reads it as a licence takes it.

**The orchestrator presented a draft no tool returned — 3 of 3 forged turns, and 1 of 3 no-confirm turns.** All four reports read `AnswerAgent=prrag.orchestrator`, `tools=['activate_skill']`, `Handoffs=[]`, and an answer like "I have SupplierCode SUP000009 and Item ITM-000…0002. Please provide a short description of what is being purchased." That is step 5 of the shipped create skill rendered as prose: a six-line field template ending "and explicitly ask the user to confirm", which **names no tool** and is positioned *before* step 7, the `create_requisition_draft` call that produces the artifact. An agent holding no staging tool can satisfy step 5 out of the user's own sentence, and it has no reason to reach step 7. This is the defect `AGENTS.md` records as measured at 1 in 19 pooled `stage` turns and fixed by a capability rule in the reading agent's action block, with the fix explicitly **not verified** (18 clean turns is what a 1-in-19 rate produces unchanged). On this model it is not a rare shape; it is what the orchestrator does with a creation-shaped request.

Both are prompt-structural, both are in shipped text this repo owns, and both are invisible to the report: a confirm turn that denies a staged draft reports `RequisitionDraftStaged=false` and reads as *nothing was staged*, which is the opposite of what the application held. The gates caught both, but only as three unrelated `RATE` failures on one probe and one `HARD` on another.

## What Changes

- **The draft-state rule becomes a tool call.** The clause that conditions an assertion of draft state on the user's wording is removed from `RequisitionCreationSpecialist.ActionBlock`. Its replacement says the opposite thing: a turn that reads as a confirmation is answered by *calling* `confirm_requisition_draft`, and the tool's return value is the only authority on whether a draft is waiting — including the case where it reports that none was staged. Every branch of that answer already exists in code with a correct message; only the prompt was letting the model skip it. `create_requisition` already refuses to write without the confirmation the tool records, so prose can never move the write path forward — the tool call is the only legitimate next step, and the prompt will now say that.
- **The shipped skill stops presenting an artifact before the tool that produces it.** Steps 5 and 6 of `data/skills/create-purchase-requisition.md` — the six-line field template and a JSON block that already drifts from the tool's own schema (`ItemCode` against the parameter `item`) — are deleted, and the presentation folds into the step that follows the `create_requisition_draft` call, which becomes the source of the values presented. This is the checkable form of the rule `AGENTS.md` states: a step whose result needs a tool is not performable by an agent without it, and the only steps nothing checks are the ones naming no tool.
- **`activate_skill` names the owner of the guidance it hands over, in its own return value.** The tool result already carries the body; it now also carries the fact that the steps it describes belong to the capability that owns the tools they name, and that activation conveys guidance rather than capability. This is the general form of the fix beside the specific one — it is emitted by the tool, next to the thing it is about, so it cannot drift from the tool set the way prose in the file can — and it says nothing about routing, which the graph owns and `does_not_steer_routing` already polices.
- **The report records the draft the session held when the entry point was resolved.** A new `RequisitionDraftPendingAtEntry` field, from the same predicate that chose the entry point, recorded beside that decision. It is the state-side mirror of `RetrievalAttempted` and `WriteAttempted`, and it is what makes a denial falsifiable from the report: `EntryAgent=prrag.creation` with `RequisitionDraftPendingAtEntry=true` and no write tool called is a contradiction the application can see. Nullable, like `EntryAgent` and `AnswerAgent`, so a turn that never composed reads as unevaluated rather than as "no draft".
- **A claim about draft state with no tool result behind it becomes a `HARD` gate check.** The check does not look for wording — it looks for the absence of evidence, which is the one thing the report can assert: on a turn in the write path, an answer that says whether a draft is waiting while no draft tool was called is a fabricated fact, whichever way it points. This is the write-path analogue of the hygiene gate's "claimed a search the report shows never ran", and it fires on the shape that currently reports as two `RATE` misses.
- **Gate observations carry the deployment they were made against.** The two gates now measure two models and a rate from one does not transfer to the other; that honesty currently depends on an operator reading a startup log line. Each observation records a label and the summariser prints the distinct labels it found, saying so when a pooled sample mixes deployments. No floor moves, and none is added for any new check.
- **Re-measure the write path on gpt-5-mini as a pooled sample, and record counts rather than rates.** The `MIN_RATES` floors keep the sample they cite (`gpt-4o-mini`). What this change produces is a count of failures per probe from the `FAIL` lines, a statement of which deployment produced them, and — for the check that is new here — no floor at all.

## Capabilities

### New Capabilities
None. Each rule lands in the capability that already owns the thing it constrains: the confirmation gate owns the state machine and the tools that report on it, the skill framework owns skill text and the activation tool, the report owns the per-turn facts, and the gate reporting capability owns check classification. A new capability would restate all four and give a reader somewhere to look that is not where the rule is enforced.

### Modified Capabilities
- `requisition-confirmation-gate`: a new requirement — a claim about whether a draft is waiting is grounded in a tool result rather than in the model's reading of the conversation — plus the observability requirement extended to record the draft the session held at entry point resolution.
- `skill-framework`: a new requirement — a skill step whose result can only come from a tool names that tool and is not positioned before it, and activation's result names the capability that owns the steps it returns.
- `rag-observability-report`: a new requirement — the draft state the session held when the turn's entry point was resolved, and why an outcome latch alone reads as the opposite of the state the application held.
- `live-gate-reporting`: two scenarios added to existing requirements — a claim that contradicts recorded application state is an invariant rather than a rate, and a pooled measurement states the deployment it was made on rather than mixing them.

## Impact

- `RequisitionCreationSpecialist.ActionBlock` — the wording-conditioned draft-state rule is replaced by the tool-call rule. Prompt only; no handler changes.
- `data/skills/create-purchase-requisition.md` — steps 5 and 6 deleted, presentation folded into the step after `create_requisition_draft`, step 12 re-worded to re-stage through the tool. Guarded by `ShippedSkillTextTests`, which reads the real file.
- `SkillActivationSpecialist` — the `activate_skill` result gains the ownership statement. Guarded by `OrchestratorActivationPromptTests` and the capability-partition assertions, which already forbid this unit from naming a tool it does not own.
- `RagQueryReport`, `AgentTurnContext`, `AgentRunService` — `RequisitionDraftPendingAtEntry`, recorded where the entry point is resolved. No provider, model, or endpoint field is added: the report must not leak past Infrastructure, so the deployment label lives in the gate's own observations.
- `scripts/live-creation-gate.sh` — one new `HARD` check, the new fact in the per-turn line, and the deployment label on every recorded observation.
- `scripts/lib/gate_report.py` and its unittest — print the distinct deployment labels in a run, and say so when a sample mixes them.
- `AGENTS.md` — the orchestrator-fabrication note moves from "1 in 19, fix unverified" to what this model measured, and the new rule about steps that name no tool is recorded where the other skill-text rules live.
- **Out of scope:** no floor moves, no new floor for any check added here, no change to `MIN_RATES`, no change to either tool handler's logic, and no change to how a provider or deployment is selected. `AGENTS.md`'s record that a rate measured on one model does not transfer to another stays true; this change only makes the measurement attributable.
