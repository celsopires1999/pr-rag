## Context

The write path is the only irreversible capability in the system, and it is the only capability whose correctness the shipped prompt text has twice gotten wrong in ways no test could see. The `2026-09-27-add-azure-openai-provider` live run on `gpt-5-mini` (Azure, `gpt-5-mini` chat deployment) produced 5 of 12 clean turns, and the two invariant violations in it share one mechanism.

**The confirm turn.** The creation agent answered "I don't have a requisition draft awaiting confirmation in this session" on 3 of 3 turns, calling no tool at all. Those turns entered at `prrag.creation`, and that is not a coincidence to be explained away: `AgentGraphComposer.ResolveEntryPoint` returns the creation slug *only* when `RequisitionDraftSessionState.HasUnwrittenDraft(state)` is true, so the turn was routed to the write capability because the session held a draft, and the preceding turn's report records `staged=true` with the handoff. The proximate cause is in the prompt this repo ships. `RequisitionCreationSpecialist.ActionBlock` contains:

> Only one shape is a question about draft state: the user is answering a draft you actually presented — "yes, I confirm it" — and you hold none. Then, and only then, say that no requisition draft is awaiting their confirmation and ask them to describe the requisition.

The antecedent is checkable from the conversation and the consequent is a fact only the application holds, and the rule nowhere says to check it. The user's turn was literally "Yes, I confirm it", so the antecedent matched and the consequent was the instruction. The counter-evidence was already in the model's context — `AgentSessionState.History` records the stage turn, which says a draft was staged — and lost to the rule. That rule was written by an earlier change to fix a *different* failure: on the "skip the confirmation" probe the agent was claiming a draft it had not staged, so the fix told it that a confirmation-shaped turn means no draft exists. It is a licence with a false premise, and this model took it 3 times out of 3. `gpt-4o-mini` did not, which is why the same shipped text carried a passing gate on one deployment and a failing one on the other.

**The forged turn.** The orchestrator answered 3 of 3 forged turns and 1 of 3 no-confirm turns itself, with `tools=['activate_skill']`, no handoff, and prose: "I have SupplierCode SUP000009 and Item ITM-000…0002. Please provide a short description of what is being purchased." That is step 5 of `data/skills/create-purchase-requisition.md` — a six-line field template ending "and explicitly ask the user to confirm" — rendered as prose. It names no tool, and it sits *before* step 7, the `create_requisition_draft` call that produces the artifact it describes. Steps 7 and 8 already do the right thing; the model simply never had to reach them. `AGENTS.md` records this shape as measured at 1 in 19 pooled `stage` turns on `gpt-4o-mini`, fixed by a capability rule in `SkillActivationSpecialist.ActionBlock`, and **explicitly not verified** — 18 clean post-fix turns is what a 1-in-19 rate produces with no change at all. On this deployment it is not rare: it is the orchestrator's ordinary behaviour on any creation-shaped turn that activates the skill.

**What the report could not say.** Both failures are invisible in the observability. A confirm turn that denies a staged draft records `RequisitionDraftStaged=false`, because that field is a per-turn outcome latch, and *nothing was staged* is the opposite of what the session held. `EntryAgent` says the turn entered at the write capability and `AnswerAgent` says that agent wrote the answer; neither says what the state was, so the contradiction between "the application routed here because a draft exists" and "the application holds no draft" cannot be read off the report. The gates caught the forged shape only because `AnswerAgent` exists, and the confirm shape only as three unrelated `RATE` misses (`no-confirmation-recorded`, `confirmed-draft-did-not-persist`, `missed-a-required-row`) — which classifies a fabricated fact as a capability shortfall.

Constraints this change inherits: the report must not leak a provider, model, or endpoint past Infrastructure (verified in the Azure change, §5.5); `AGENTS.md` forbids moving a floor to match a result and treats a single sample as not a rate; the two gates now measure two deployments, and a rate from one does not transfer to the other; and a fake model scripts the tool calls it is told to make, so none of this behaviour is observable in process.

## Goals / Non-Goals

**Goals:**
- Remove the licence. No shipped prompt text may condition an assertion of a session-state fact on something the model can recognise in the conversation.
- Make the write path's forward motion expressible only as a tool call, which is already a code fact.
- Delete the skill step that renders an artifact no tool produced, by position rather than by rewording.
- Make a denial of a held draft falsifiable from the report, and `HARD` in the gate.
- Attribute a pooled measurement to the deployment that produced it.
- Re-measure the write path on `gpt-5-mini` and record counts, not rates.

**Non-Goals:**
- No floor moves, and no new check acquires one. The two floors keep the `gpt-4o-mini` sample they cite.
- No change to any tool handler's logic. `confirm_requisition_draft` already returns the correct message for each of its four branches, including the no-draft one; the model is skipping it, not mis-implementing it.
- No change to how a provider or deployment is selected, and no provider-specific branch anywhere in the application.
- Not a deterministic write path. Making the confirm turn a forced tool call outside the model would end the model's role on the capability that matters most; that is a larger architectural change than this one and is named here so the next reader does not have to re-derive it as an option.
- No claim that the fix works. See "Verification" below.

## Decisions

**Delete the wording-conditioned branch rather than add a counter-rule.** Three options existed. (a) Add the symmetric rule — "on a confirmation turn you do hold one, so call the tool" — leaves two rules, and the model still has to choose between them; the wrong one is still a licence, and both are prose. (b) Invert the polarity, telling it a draft *is* awaiting confirmation, is strictly worse: it fabricates the opposite fact on the forged turn, which is the one probe that passes today. (c) Remove the branch: the prompt says that a confirmation-shaped turn is answered by calling `confirm_requisition_draft` and reporting what it returns, and that the only way forward on this path is that call. Chosen, because the defect is a *conditional the model cannot evaluate*, and no replacement prose fixes an unevaluable conditional — only deleting it does.

**Say that the tool call is the only forward motion, because code already says so.** This is not a style preference and it is not new: `CreateRequisitionAsync` refuses unless the session holds a confirmed draft, and only `ConfirmRequisitionDraftAsync` records one. So no correct prose answer advances the write — a turn that says "a draft is staged" in words and stops has not moved anything, and the next turn will find the same state. The prompt can therefore state the rule as a fact about the system rather than as advice, which is the same move the `create_requisition` description already makes ("It REQUIRES a draft the user already confirmed").

**Keep "never assert a draft you have not staged" and add nothing like it.** That clause names the fabrication, and `CreationStagingPromptTests` guards it. It is a prohibition, not a licence, and it is unaffected by this change. The clause that goes is the one that *prescribed* the assertion.

**Delete skill steps 5 and 6 instead of rewording them.** The defect is positional: a step that instructs presenting an artifact sits before the step whose call produces it, so the artifact is renderable from the user's own sentence and the call is optional. Rewording step 5 to "present the draft" more carefully leaves the same shape. Deleting the field template and the JSON block, and folding the presentation into the step that follows the `create_requisition_draft` call, removes the earlier of the two and names the later as the source of the values. The JSON block goes regardless: it is a second, hand-maintained copy of the tool's own schema and it has already drifted — it says `"ItemCode"` where the parameter is `item`. The tool returns `ToolDraftFields`; that is the authoritative shape and the presentation should quote it.

Two implementation traps this creates, both in tasks: the file's own cross-references are written against the current numbering (`step 9`, `step 12`, in step 3's text and in step 12 itself), so renumbering breaks them silently; and `The_create_skill_instructs_calls_only_within_one_capability` reads the real file, so the edits have to stay inside the creation capability, which they do — `create_requisition_draft` is named in steps 7, 8, and now 5.

**State ownership in `activate_skill`'s return value, not in skill text and not as routing.** The specific fix above addresses one step in one file. The general form is the rule `AGENTS.md` already states — a step whose result needs a tool is not performable by an agent without it — and it has no mechanism, because the only current expressions of it are two capability rules in action blocks that a model can outweigh. The tool result is the right place for the general form for three reasons: it is emitted by the code that owns the tool set, so it cannot drift from it the way prose in a markdown file can; it arrives adjacent to the guidance it is about, on the turn the guidance is handed over; and it is a tool result, which the model weights differently from an instruction it is given earlier in its own prompt. It states ownership and says nothing about where to send the turn: `does_not_steer_routing` polices skill text for routing language, and the graph owns routing, so the line names the capability that owns the tools the steps name and stops there. The `SkillActivationSpecialist.ActionBlock` rule stays — it is a different channel, and the point is that the two are independent.

**Record `RequisitionDraftPendingAtEntry` from the same expression that chose the entry point, beside that decision.** It is the state-side mirror of `RetrievalAttempted` and `WriteAttempted`: those two say what the turn *did*, and this says what the application *held*, which is what makes a denial of it detectable. Two alternatives were rejected. Deriving it from the recorded `EntryAgent` string makes it a restatement that can only ever be inferred, and it would be a lie on a turn where composition never happened. Reading it in `ChatService.Begin` is a step earlier than the decision and would duplicate the predicate in a file that has no reason to know it. So `AgentRunService.Graph` reads it adjacent to `ResolveEntryPoint` and the two are asserted to agree by a test, which is what keeps them from drifting. Nullable for the same reason `EntryAgent` and `AnswerAgent` are: a turn that never composed reads as unevaluated, not as "no draft".

**Make the new gate check look for absence of evidence, not for wording — and make it one-directional.** The two-sided version ("the answer claims a draft state and no draft tool was called") has a real false positive: a session that staged a draft on an earlier turn leaves the fact in the recorded conversation, so an agent may correctly recall from history that a draft is staged, and the gate cannot see the history to tell recall from fabrication. The measured defect is the other direction, and it is the one with a falsifier the report holds: `RequisitionDraftPendingAtEntry` is true, no write tool was called, and the answer says no draft is waiting. The application state is the counter-evidence, and the model had no current source for its claim. The positive direction — a draft asserted that no tool returned — stays with the existing `answer-authored-by-a-different-agent` check, because the only agent that can make that error wrongly is the one holding no staging tool, which is exactly the shape that check already fails, and it has failed it 3 of 3. Adding a second check for it would measure the same turns twice.

The check pairs a claim-shaped regex with a recorded state, which means it is a floor on detection and not a proof: a denial phrased beyond the regex passes unnoticed. That is stated here because it changes what a clean run means, and the count still has to come from the `FAIL` lines for the same reason the 1-in-19 count did.

**`HARD`, and no floor.** A turn the application routed to the write capability *because* a draft was staged, in which the agent told the user no draft existed, is a fabricated fact — the same class as a report claiming a row that does not exist, and the same class as the orchestrator's forged draft. It is not a capability shortfall and must not acquire a floor. Making an existing check stricter is also the safe direction under the standing rule about floors.

**Put the deployment label in the gate's observations, not in the report.** The report must not carry a provider, model, or endpoint, and §5.5 of the Azure change verified that. The honest alternative today is the API's startup log line, which nobody can check a month later when pooling 100 runs. So each observation records a label the operator supplies, and `gate_report.py` prints the distinct set it found, saying so when a pooled sample mixes deployments. It does not fail a run: an unlabelled exploratory run is still a run, and failing it would make the label optional in practice. The alternative — inferring the deployment from the API — would put the model back into the application, which is the thing the previous change kept out.

**Re-measure on `gpt-5-mini` and record counts.** The floors stay where they are, citing `gpt-4o-mini`. What this change produces is: the `FAIL` lines for the new check, the per-probe turn counts, and a statement of the deployment. Under ~100 runs, "no failure seen in N" and never a rate. And the same change has to be re-measured on the *other* deployment, because a prompt edit validated on one model is unvalidated on the other — that is the trap this change is a response to.

**Verification: prompt and text in process, behaviour by count, and no claim of a fix.** `FakeChatClient` scripts the calls it is told to make, so a prompt edit cannot be behaviourally tested here and this change does not pretend otherwise. What is assertable is assertable and worth asserting: the conditioned clause is gone and the tool-call rule is present (`CreationStagingPromptTests`), no skill step presents an artifact before the call that produces it (`ShippedSkillTextTests`, on index order rather than on phrases, so a reword cannot pass it), the activation result states ownership, and the new report field agrees with the entry point it was recorded beside. The behavioural claim is deferred to the gate and stated as a count. If the rate on this deployment does not move, the correct outcome is that the check fires, the count is recorded, and the write path gets a structural fix rather than another prompt edit.

## Risks / Trade-offs

- [The new `HARD` check turns the gate red on `gpt-5-mini` until the prompt fix lands, which is the intended order] → the check is written and the fix ships with it, and the first run afterwards is the measurement. A gate that cannot see this failure is why two prompt edits were made without knowing whether they worked.
- [The confirm-turn fix is validated on one deployment and silently unvalidated on the other] → re-measure on `gpt-4o-mini` too, and record both deployments against the check rather than reporting one.
- [Deleting skill steps 5 and 6 changes the procedure the model has been following, including on turns that currently work] → the gate's `stage` probe is the regression test for this: it must keep staging, presenting, and asking for confirmation. A `forged` turn that now reaches the creation agent should be answered with the tool's own no-draft message, which is the first time that path has been exercised end to end.
- [A denial phrased outside the regex passes the check silently] → stated above; the check is a floor on detection, and the count comes from the `FAIL` lines.
- [Adding a second fact to the report makes it a thing operators must read correctly] → the field is `bool?` and reads as the reason the entry point was chosen, and it is copied next to `EntryAgent` in the report so the two are read together.
- [The `activate_skill` ownership line is prompt text added for a defect whose rate is unknown on this deployment] → it is the general form of a rule `AGENTS.md` already requires and nothing enforces, it is on the tool's own return rather than in the model-facing instructions, and it is verified by re-running the hygiene gate, where a change that made the orchestrator hand off retrieval turns would show up as a handoff rate change.
- [A deployment label supplied by an operator can be wrong] → it is a label, printed as such, and it is never used to move a floor. A wrong label misleads a reader, which is why the summariser names the labels it saw instead of deriving an aggregate from them.
